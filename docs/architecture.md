## 三、一次问答的数据流

1. 用户提问 → 意图路由；
2. LLM 模式：模型输出 JSON 工具计划；无 Key：规则 Agent 按关键词分支产出同一格式计划；
3. 工具并发执行（`asyncio.gather + to_thread`），政策工具内部走检索；
4. 检索返回分块 + 原始余弦置信度；低于阈值 → 拒答或退化为纯数据回答；
5. 综合回答；引用由代码从工具结果确定性提取；
6. 写 SQLite trace（问题、工具调用、延迟）。

## 四、关键决策与取舍

### 1. 为什么用"JSON 工具规划"而不是原生 Function Calling

- 计划是纯数据，可校验、可回放、可评测；
- 换模型/换厂商不需要改工具层；
- 代价：模型偶尔输出非法 JSON，需要解析失败兜底（不把异常文本写进对话历史）。

### 2. 为什么保留规则 Agent

演示环境无法保证有 LLM Key 或网络；规则版提供确定性基线，让"工具路由"这一层可以独立评测和回归。
两套模式共享同一工具注册表，避免两套业务逻辑漂移。

### 3. 为什么引用由代码生成

实测发现模型会编造库外标准号、把标准号当条款编号写进引用。所以：**API 层引用 = 代码从工具结果
确定性提取，幻觉恒为 0**；模型自由文本里的引用不可信，不作为对外依据。

### 4. 为什么强调"阈值随语料漂移"

知识库从 1102 字扩到 4199 字后，BGE 的可行拒答阈值区间从 `(0.409, 0.537)` 漂到 `(0.489, 0.567)`，
旧阈值直接掉出区间，拒答准确率从 0.958 跌到 0.771。结论：**任何语料/分块改动都必须重新标定阈值**，
这条约束写进了配置注释。

### 5. 为什么是进程内 NumPy 索引而不是向量库

演示规模（11 篇条款、几千字）用内存索引足够，省掉部署依赖；代价是数据量扩大后需要换成
pgvector/Milvus——这是已记录的演进项，不是"没想到"。

### 6. 并发优化的诚实结论

工具是 pandas/sklearn 的 CPU 密集型，`asyncio.to_thread` 受 GIL 限制，实测加速只有 1.18–1.20×；
不用进程池是因为工具依赖模块级 DataFrame 缓存，多进程会重复加载数据。**这个结论比"优化了 3 倍"更可信。**

## 五、已知边界

- 知识库仅 11 条条款，用于演示 RAG 边界，不代表完整法规系统；
- 实时链路依赖第三方 Token，未配置时走历史数据回退；
- 预测是统计学习，不含未来气象输入，极端天气响应有限；
- trace 用 SQLite，生产应换可观测存储。
